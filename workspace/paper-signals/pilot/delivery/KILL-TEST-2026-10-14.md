# Kill-mid-flight test — v2 hardened delivery worker — 2026-10-14

**Scope honesty first:** the production worker is an LLM agent executed by the
cron controller — it cannot be `kill -9`'d from here. This test exercises the
v2 procedure's state machine (`WORKER-SPEC-v2-2026-10-14.md` §§1, 6, 7) in a
sandbox: `worker_sim.py` implements the checkpoint state machine against a
fake ledger, fake transport outbox, and fake append-only chat channel (which,
like the real side chat, does NOT dedupe on `(signal_id, alert_type)`). The
kill lands AFTER emission (alert text appended to the fake channel) but BEFORE
the ledger write — the exact race in Logan's correction. **This is
sandbox-only evidence for the procedure logic, not deployed proof.**

Test scripts: `kill-test/worker_sim.py`, `kill-test/recover.py`,
`kill-test/run_kill_test.sh`. Raw evidence: `kill-test/evidence/scenario-A/`,
`kill-test/evidence/scenario-B/`.

## What was done

1. `worker_sim.py` ran the v2 step order with atomic checkpoints
   (tmp-file + rename): `config_loaded → status_fetched → ack_swept →
   send_swept`, rendered one `SETUP_PENDING` alert (`sig_killtest_001`) into
   the fake channel, wrote the `alerts_rendered` checkpoint, then parked at
   the killpoint.
2. The driver sent `kill -9` to the worker PID while parked (post-emission,
   pre-ledger-write). Checkpoint at kill: `steps=[config_loaded,
   status_fetched, ack_swept, send_swept]`, `alerts_rendered=
   [sig_killtest_001/SETUP_PENDING]`, `ledger_keys_written=[]` — the
   rendered-but-unlogged state.
3. `recover.py` (v2 §7) reconciled the key against the fake outbox, then ran
   a second time to prove recovery idempotency.

## Scenario A — transport HAD relayed the killed run's output

Outbox row (set post-kill, mirroring the real 2026-10-14 rows which were
created at `finished_at` and delivered minutes later): `state='delivered'`,
`delivered_at_utc` set.

| Assertion | Result |
|---|---|
| chat emissions after kill + 2× recovery | exactly 1 (no duplicate) |
| ledger entries for the key | exactly 1 |
| delivery_status | `awaiting-ack` with linked delivery_key + ack_evidence |
| surfacing lines | 0 (nothing to surface) |

The alert was NOT lost (recorded with ack evidence, no re-send needed) and
NOT duplicated (recovery reconciled instead of re-emitting; second recovery
run changed nothing).

## Scenario B — transport ambiguous (Logan's correction case)

Outbox row exists but `state='dispatching'`, `delivered_at_utc=null` — the
channel cannot confirm whether the rendered output landed.

| Assertion | Result |
|---|---|
| chat emissions (original only) | exactly 1 (no blind re-send) |
| ledger entries for the key | exactly 1 |
| delivery_status | `unknown` (NOT delivered, NOT failed, attempts=0) |
| surfacing lines | exactly 1 — `PAPER delivery UNKNOWN — operator review: sig_killtest_001/SETUP_PENDING (…NOT re-sent, NOT marked delivered)` |
| run log `controller_status` | `timeout` — separate field, never mixed into delivery_status |

No silent loss: the emission exists in the channel record, the ledger holds
the key as `unknown` with the reason, and exactly one operator-review line
was surfaced. No blind duplicate: recovery did not re-emit. No false
delivery claim: `delivered` was never written without ack evidence. Second
recovery run: still 1 emission, still 1 ledger entry, still 1 surfacing line.

## Conclusion

The v2 procedure satisfies Logan's corrected acceptance criterion: where the
channel can confirm (outbox delivered), the alert is reconciled without
re-send; where it cannot, the ledger records `UNKNOWN`, surfaced once —
never silently retried as if unsent, never marked delivered without evidence.
`controller_status` and `delivery_status` remained separate in every record.
